端侧克隆的\"语速忽快忽慢\"来自三件事，2026-11-13 用 18 字中文（`今天天气不错，我们一起去公园散步吧。`）+ `files/ref.wav`（2.69 s，67 帧）扫点定性。

## 扫点实测（single job，目标帧数用 `--ei frames N` 强制）

| N | 输出 | 有声 | 字/秒 | 频谱包络 |
|---|---|---|---|---|
| 80 | 3.28 s | 2.78 s | 6.5 | 连续，中间一个 0.2 s 停顿 |
| 98 | 3.19 s | 3.19 s | 5.6 | 连续 |
| 115 | 4.08 s | 3.99 s | 4.5 | 中间插了 ~0.9 s 静音 |
| 135 | 4.79 s | 4.70 s | 3.8 | 中间插了 ~1.5 s 静音 |
| 145 | 5.56 s | 5.47 s | 3.3 | 前 1.3 s 是 -40 dB 噪声 + 中间 1.5 s 静音 |

**关键：活跃语音时长（-35 dB 以上的段）在所有 N 下都是 ~2.3–2.6 s，峰计数都是 24–26 个。**
即 **N 不改变局部语速，只改变停顿的分布/长度**；N 偏小先吃掉停顿、再压缩语音（就是 2026-11-07 那个 14 字/秒的 bug）。

参考音本身：2.69 s / 活跃 2.20 s / 24 峰（10.9 峰/秒），与输出一致 → **局部语速是从参考音克隆来的**，不是估计出来的。

## 结论

1. **静态长度不是语速的根因**：图只固定窗口 S，目标帧数 N 是运行时变量。真正的坑是 `Prompt.planClone` 把 `want` 夹到 `DEFAULT_FRAMES=200`（解码器上限）→ 长文本一律被压成 200 帧 = 8 s，48 字以上必然压缩。
2. 估大只是把停顿拉长，估小才压缩 → 仍应\"宁长勿短\"，但**不能靠尾部裁剪补救**（多余帧大多变成中段停顿，不是尾部静音）。
3. 参考音语速重载 `Duration.frames(text, refText, refFrames)` 默认没启用（refText 可空）→ 不同说话人只能吃全局常数（4.7 字/秒，偏快）。

## 端侧落地（`~/projects/viitorvoice-demo`，2026-11-13）

- `text/Split.kt`：按句（。！？!?；…）→ 分句（，、,：:）→ 硬切分三级切块，每块保留开头情绪 tag；合并回能放下的邻居。
- `audio/Render.kt`：`trimEdges`（10 ms 窗、-45 dB、留 30/60 ms）、`voicedSec`、`concat`。
- `HomeViewModel.runClone`：
  - `est ≤ 200` 走单 job（行为不变，只是多了分段日志）；
  - 否则按块循环：每块用**实际 cond 长度**算 room，放不下就再切一次；参考音每块保留 `min(refFrames, 100)` 帧；每块 `clonePrepare`→32 步→`finishToWav("clone_p{i}.wav")`；
  - `assemble()` 逐块 `trimEdges` → `concat` → 写 `clone.wav`，日志输出\"N 段 · 秒 · 有声秒 · 字/秒\"。
- 50 字 / 9.5 s 目标 → 3 段（18+22+9 字），输出 8.89 s、5.5 字/秒、总耗时 19.97 s（每段 NAR ~6.5 s，S=256 固定成本）。
- 调试入口：`am start -n com.viitorvoice.demo.tmp/com.viitorvoice.demo.MainActivity --es ref <wav> --es text "…" [--es reftext "…"] [--ei frames N]`（`vm.debugClone`）。
